# Development instructions

- Keep repository documentation, code comments, commit messages, and pull-request descriptions in English.
- Follow the milestone dependencies and acceptance gates in `docs/roadmap.md`. Do not mark a milestone complete while any required deliverable or validation remains unfinished. Record observed failures and unsupported features explicitly.
- Implement the project-owned core selected in `docs/design/own-core.md`. Keep wazero and other engines as independent semantic and performance references. Do not replace the core with an engine wrapper or silently fall back to a competitor when a backend lacks a feature.
- Treat interpreter throughput and native compilation/execution as required core deliverables. Follow `docs/design/core-compiler.md`, `native-abi.md`, and `performance-contract.md`; a small instruction subset or a passing microbenchmark does not complete a profile or milestone.
- Keep one active contribution PR at a time unless the user explicitly requests parallel PRs. Preserve later work on branches and merge the current PR promptly once its final checks pass and review findings are resolved.
- Under the owner decision of 2026-11-11, prioritize Go-compiled wasmvm reaching competitor performance before dedicated LLGo optimization. Keep LLGo semantic compatibility and the pinned production profile; report unresolved controls and reject unproven performance expansions.
- Under the owner decision of 2026-10-31, complete all remaining functional capabilities before performance optimization. Continue implementation through the remaining stages without stopping at each merged increment. Keep semantic validation, Go/LLGo compatibility, coverage and necessary regression checks; defer optimization and broad competitive measurement campaigns until capability coverage is complete. Existing performance failures and regressions remain recorded, and performance acceptance stays open. Architecture problems that prevent correct, bounded execution remain blocking.
- Keep the architecture compact and extensible: share compiler stages and runtime contracts, avoid workload-specific fast paths and duplicate execution frameworks.
- Under the owner decision of 2026-11-14, investigate every observed performance regression, including rejected experiments. Treat LLGo as an evolving compiler: distinguish runtime work, generated code, register allocation, dispatch and layout effects; preserve inconclusive evidence and report remaining causal gaps. Produce a minimal reproducer and an LLGo issue when compiler evidence supports one.
- The 2026-11-01 mandatory functional scope also includes Compact Import Section, Wide Arithmetic, Custom Page Sizes, non-JavaScript Custom Descriptors, and Stack Switching. Keep their pinned proposal snapshots and feature gates distinct from Core 3.0. Complete both backends and Go/LLGo execution before claiming each extension complete.
- The owner requests 5–10 minute CI jobs. Keep every package in the dual-compiler/platform semantic matrix; validate LLGo shard completeness, retain the pinned release profile, and measure compilation/linking separately from test execution. All shards and shared checks must pass before merging.
- Keep CI proportional to the change. Preserve the full Go/LLGo semantic matrix; centralize shared pure-Go quality checks and use the declared PR benchmark scope. Run full sustained/controlled performance suites for their explicit acceptance purpose, not redundantly after every PR and merge.
- Make changes on a contribution branch and submit a pull request. Do not push implementation changes directly to `main`. Merge only after the final PR head has passed its required checks and review findings are resolved.
- Compile and execute shared semantic tests with both Go and LLGo. A successful build, an expected incompatibility assertion, and actual guest execution are different outcomes; report them separately.
- Use the pinned LLGo release profile (`-O3 -lto=full`) consistently for supported semantic CI, engine/CLI benchmarks and native probes. Record compiler/profile upgrades as separate baseline events, apply identical flags to source base/head, and retain default-flag regressions as diagnostics.
- Test successful behavior, invalid input, resource limits, cleanup, cancellation, and feature interactions as applicable. Do not hide compiler failures with broad skips or `continue-on-error`.
- Report coverage for the exact packages measured. Statement coverage of an evaluation harness is not coverage of wazero, instruction semantics, or the Wasm specification. Keep the evaluation harness at or above the CI threshold; justify any future threshold change in its PR.
- Pin candidate engines, test producers, fixtures, and toolchains. Keep provenance, checksums, and licenses for reused assets. Use temporary copies for diagnostic dependency patches; never modify a shared Go module cache.
- Treat experimental patches as evaluation evidence until their full production contracts are implemented and validated. Preserve the distinctions between host GC, guest linear-memory GC, and WasmGC; likewise distinguish Core Threads, legacy wasi-threads, and component async.
- Follow the repository-owner write policy supplied by the user. Changes to external upstream repositories require an allowed-fork contribution PR; permission to merge this repository's PRs does not authorize merging external upstream PRs.
