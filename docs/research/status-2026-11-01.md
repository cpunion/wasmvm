# Standards and implementation audit: 2026-11-01

This audit separates proposal maturity, declared implementation, executed tests,
and performance acceptance. The engine snapshot is
`4ad69c24de32a96310799ad76bd10af118afed42` (PR #84). Documentation and
benchmark adapters added by this audit do not change that engine.

## Current standards

Core **3.0** is complete at the Community/Working Group feature level. The live
specification is Release 3.0, dated **2026-10-28**; the W3C publication is still a
**Candidate Recommendation Draft**, not a Recommendation. The Core binary
header remains version 1. Sources: [live spec](https://webassembly.github.io/spec/core/),
[W3C publication history](https://www.w3.org/standards/history/wasm-core-2/).

The official proposal register currently contains **20 finished entries**,
**31 active entries** (Phase 5: 2; Phase 4: 3; Phase 3: 4; Phase 2: 9; Phase 1: 13),
and **10 inactive entries**. Phase 0 ideas are tracked separately and are not an
enumerable set of adopted commitments. Phase 5 entries in the active table have
completed WG standardization but await integration; finished entries are already
integrated. Sources: [register at df6a2aca](https://github.com/WebAssembly/proposals/tree/df6a2aca1cd9d779eb4f2f3e19dae8277f336015),
[phase process](https://github.com/WebAssembly/meetings/blob/main/process/phases.md).
The register did not change between the October 26 survey and this recheck.

Latest released WASI series: **0.2.12** (2026-06-02) and **0.3.2**
(2026-10-13). WASI 0.3.0 shipped on 2026-06-11. No WASI 1.0 release is
listed. P1/P2/P3 mean Preview 1/2/3; they are not WASI semantic versions 1/2/3.
Sources: [official releases](https://github.com/WebAssembly/WASI/releases),
[0.3.2](https://github.com/WebAssembly/WASI/releases/tag/v0.3.2).

## Every finished proposal: wasmvm support

“Implemented” means the declared binary profile executes under both the
interpreter and owned native compiler, with Go and pinned LLGo, on Linux amd64
and macOS arm64. Core 2 is the default; Core 3 extensions require the Core 3
profile or corresponding feature flags. It does not imply performance parity,
a complete JavaScript/Web API, or an owned WAT parser.

Evidence: the complete pinned [Core 2 inventory](../../testdata/core2/README.md)
contains **51,139 binary assertions / 148 scripts**; the complete pinned
[Core 3 inventory](../../testdata/core3/README.md) contains **61,395 / 259**.
Each interpreter/native tier executes the full inventory; source text-parser
commands are counted separately. The final-head
[four-job CI run](https://github.com/cpunion/wasmvm/actions/runs/41290134564)
passed under both host compilers and platforms. These are exact pinned-suite
results, not certification of every future edit to the live specification.
[Feature flags](../../pkg/wasm/features.go), [GC contract](../design/wasm-gc.md)
and [compiler design](../design/core-compiler.md) describe the implementation.

Three finished entries need distinct treatment: JS BigInt and JS String
Builtins are unimplemented embedding APIs; custom text annotations depend on
external tooling. Branch hints preserve execution semantics by being ignored.
Consequently “all finished proposals including browser/text APIs” would be an
incorrect support claim, even though the declared Core binary profile passes.

conformance certification**. Y = reported support; F = explicit feature flag;

not applicable. Do not interpret an absent registry entry as a failure.
Wazero is v1.12.0, Wasmtime v48.0.1, Wasmer v7.3.0 and WasmEdge v0.17.1.

[Wasmtime release support tiers](https://github.com/bytecodealliance/wasmtime/blob/v48.0.1/docs/stability-wasm-proposals.md),

Wasmer's disabled-by-default Memory64 switch documents intent; this audit does
not promote it to verified end-to-end compiler/table64 support. WasmEdge's
registry feature dates and its later default-enablement dates can differ.
The [release configuration](https://github.com/WasmEdge/WasmEdge/blob/0.17.1/include/common/configure.h)
is the authority for defaults, not a marketing claim of “all proposals.”

[Wago at 90f2b57](https://github.com/wago-org/wago/blob/90f2b57dafa7f8c3cc7e3aca38b91148f15e1d1e/FEATURES.md)
reports full Core 3 support, optional Core Threads, and implemented compact
imports/wide arithmetic. It remains beta, with WASI/component plugins that need
separate assessment. Its published 58,038 assertions and our 61,395 use different
suite/producer inventories and must not be used to rank conformance by count.
No fresh Wago throughput number is inferred from its published speed claims.
Browser engines and WAMR are also outside this audit's timed runtime matrix;
their absence is not a performance result.

## Inactive proposals

The 10 official entries are Unmanaged Closures, Conditional Sections, Feature
Detection, Module Linking, Interface Types, Funclets, Call Tags, Constant Time,
JS Customization for GC Objects, and Instrument and Tracing Technology.
Typed Function References supersedes Unmanaged Closures; Component Model
supersedes Module Linking/Interface Types; Custom Descriptors supersedes JS GC
Customization. No inactive encoding is adopted implicitly. Legacy EH is also
tracked separately from final EH. Source:
[inactive register](https://github.com/WebAssembly/proposals/blob/df6a2aca1cd9d779eb4f2f3e19dae8277f336015/inactive-proposals.md).

world does not use them. Source:
[official adoption record](https://github.com/WebAssembly/WASI/blob/463701e0f6c575a5d24ae31c2ec1e0ebf09d28e1/docs/ComponentModelFeatures.md).

## Remaining support and acceptance work

The declared Core 2/3, Core Threads and P1/P2/P3 functional implementations are
present. Remaining mandatory acceptance includes broader independent
conformance/interoperability, controlled performance on both platforms under
both host compilers, cancellation/scaling/peak-memory evidence, and resolution
of recorded corpus limitations. Optional Core proposals listed above are
separate scope decisions, not hidden parts of the stable profile. Performance
measurements and priorities are recorded in the accompanying
[performance audit](performance-2026-11-01.md).

The [machine-readable snapshot](proposal-status-2026-11-01.json) preserves all
61 registered proposal names/phases/URLs and the official competitor feature
cells, including flags/unknowns. Those third-party cells are reports, not test
results produced by wasmvm.
