# Existing Implementations and Reuse Assessment

Research date: 2026-10-26. This document records observations from official repositories, source code, and documentation on that date. **It is not a certification based on tests rerun by this project.** Documentation on `main` may precede released versions, and support can depend on architecture, backend, and build flags. A final selection requires pinned versions and the M0 comparison experiments.

## Findings

The Go ecosystem already has a mature pure-Go Wasm runtime, wazero, and Wago is a newer pure-Go implementation that claims WasmGC and Core 3 support. The absence of a Go implementation is not a valid rationale for this project. The project's measurable goal should be: **compile the same VM source with Go and llgo, provide explicit contracts for WasmGC, shared-linear-memory threads, and versioned WASI, and demonstrate consistent behavior with the same test corpus under both host compilers**.

Complete M0 first: assess llgo portability and reusable parts of the wazero interpreter and Wago before deciding the scope of an independent implementation. Retain the independent-interpreter design as the current baseline. Do not assume a permanent fork of an entire existing engine, or describe a Go wrapper around a Rust/C runtime as a VM implemented in Go.

## Capability matrix

Support refers only to the stated scope. **Unverified** means this survey did not find sufficient official implementation evidence for a support commitment; it does not mean the capability is absent across the ecosystem. Core threads, WASI `thread-spawn`, and Component Model concurrency are separate layers.

| Implementation | Implementation language / Go integration | WasmGC | Core threads / thread-creation ABI | WASI P1 | WASI P2 / Component Model | WASI P3 |
| --- | --- | --- | --- | --- | --- | --- |
| wazero | Go, no cgo; interpreter and native-code backend | No GC feature on main; interpreter GC PR remains open | Experimental CoreFeaturesThreads; built-in wasi-threads unverified | Built in | Built-in implementation on main unverified; third-party layers exist | Unverified |
| Wago | Go, no cgo; single-pass native-code backend; beta | Official feature table claims support; backend and object boundaries need retesting | Core threads require opt-in; feature table explicitly excludes wasi-threads | Separate experimental plugin | Separate experimental plugin; P2 command, resources, and Canonical ABI; networking denied by default | Planned in the feature table; component plugin has experimental async mechanisms |
| wippyai/wasm-runtime | Go component layer on wazero | Cannot promise more than the underlying engine supports | Not independently confirmed in this survey | Follows the underlying engine | README claims WIT, Canonical ABI, P2, and asyncify | Unverified |
| pgavlin/warp, Life, wagon | Historical Go implementations / toolkits | No evidence found of complete modern GC support | No evidence found of complete modern threading support | warp has a wasi package; others require individual verification | Unverified | Unverified |
| Wasmtime | Rust; wasmtime-go calls the C API through cgo | Tier 1 in the official matrix, with Winch coverage exceptions | Core threads Tier 2 with known resource-management limits; separate wasi-threads implementation | Supported | Supported; Component Model enabled by default | Implemented; wasi crate source still describes it as experimental, unstable, and incomplete |
| WAMR | C; Go language binding wraps the native runtime | Optional build; official documentation explicitly notes incomplete GC/Core 3 conformance | Shared memory, pthreads, and wasi-threads implemented | Supported | Native component execution / P2 unverified in this survey | Unverified |
| WasmEdge | C++; Go binds to the native API | Default since 0.16; interpreter and AOT implementations | Core threads opt-in; does not establish wasi-threads support | WASI host provided | Component **loader/validator** since 0.17, which does not imply component execution | Unverified |
| Wasmer | Rust; wasmer-go uses cgo | Current native-compiler feature set / validator does not enable GC instructions | Threads, WASIX pthreads, and wasi-threads implemented | Supported | Insufficient evidence for a native P2/component-execution commitment | Unverified |
| V8 / SpiderMonkey / JavaScriptCore | C++ browser engines, not Go VMs | Released | Shared memory and atomics; Web Workers provide lifecycle | Supplied by embedding/shims, not automatically by Core | Assess JS tooling separately from native engine capabilities | No commitment inferred from Core support |

Evidence and limitations for each row follow. This matrix is not a certification of every platform/backend combination.

## wazero: a valuable Go reference and reuse candidate

The official repository moved from `tetratelabs/wazero` to `wazero/wazero`; the module path remains `github.com/tetratelabs/wazero`. The README promises Core 1/2, an interpreter, and a native compilation backend under Apache-2.0. Pure Go here primarily means no cgo, not the absence of assembly or runtime conventions. Source: [README](https://github.com/wazero/wazero/blob/main/README.md).

Observed source snapshot: `ef2dd2f85376c1a6ff79baae0cc1a5aa42c91db7`. The stable feature set remains at Core 2. Experimental features include threads, tail-call, extended-const, exception-handling, and typed-function-references. The older blanket claim that wazero has no threads or EH is therefore inaccurate. Threading comments also distinguish guest atomic operations from host Memory API capabilities. Sources: [stable features](https://github.com/wazero/wazero/blob/ef2dd2f85376c1a6ff79baae0cc1a5aa42c91db7/api/features.go), [experimental features](https://github.com/wazero/wazero/blob/ef2dd2f85376c1a6ff79baae0cc1a5aa42c91db7/experimental/features.go).

[GC PR #2494](https://github.com/wazero/wazero/pull/2494) remained open at the research date. It describes recursive types, structs/arrays, associated validation and interpreter instructions, and use of the host Go collector. The optimizing compiler is outside its scope. An open PR is not evidence of support on main or in a release. [Core 3 tracking issue #2426](https://github.com/wazero/wazero/issues/2426) also remained open.

Start llgo evaluation with the interpreter. The decoder, validator, WASI host, specification runner, and test organization are useful references. The native backend has amd64/arm64 assembly entry points; a port must validate calling conventions, stack switching, and Go runtime boundaries rather than merely change the compiler command. Source: [amd64 ABI entry](https://github.com/wazero/wazero/blob/ef2dd2f85376c1a6ff79baae0cc1a5aa42c91db7/internal/engine/wazevo/backend/isa/amd64/abi_entry_amd64.s).

Reuse benefits include a mature embedding API, WASI P1 behavior, error classification, and test corpus. Costs include GC changes across the type system, value representation, validator, and execution engine. Much of the implementation is under `internal`, preventing ordinary direct imports; reuse may require upstream contributions, extracting libraries, or limited code imports. Include the maintenance cost of a long-lived fork in M0.

## Wago: compare it carefully before implementing a new engine

Wago is publicly described as beta. It has a Go decoder/validator and the single-pass Railshot native-code backend. WASI and Component Model support live in separate plugins. Its license is Apache-2.0; the observed go.mod declares Go 1.22 and depends on `golang.org/x/sys`. Sources: [README](https://github.com/wago-org/wago/blob/main/README.md), [LICENSE](https://github.com/wago-org/wago/blob/main/LICENSE), [go.mod](https://github.com/wago-org/wago/blob/main/go.mod).

Observed tree snapshot: `4de27acba12926e52b815e5845e035d1cf11edd0`. Its [feature contract](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/FEATURES.md) claims Core 3, including GC, typed refs, EH, memory64, and multi-memory. Core threads require explicit enablement. The same table excludes shared-everything threads and wasi-threads, and lists stack switching and P3 as planned. Its threading support must not be described as existing WASI pthread support.

The website summary and repository contracts differ in granularity. Selection should rely on concrete source and tests. For example, the [WASI plugin README](https://github.com/wago-org/wasi/blob/main/README.md) marks P1/P2 experimental. P2 supports the import surface of `wasi:cli/command`, but network calls return typed access-denied errors; legacy unstable support has been removed. Its discussion of 0.3 breaking changes refers to **the plugin's own version**, not WASI 0.3 support. The [Component plugin](https://github.com/wago-org/component-model/blob/main/README.md) includes P2, nested composition, resources, and experimental tasks/futures/streams. Those mechanisms do not establish complete WASI P3 support.

There is test evidence beyond feature claims, but it still needs independent reproduction. [SPECTEST](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/SPECTEST.md) reports a pinned Core 3 suite with 258 files, 2,226 modules, and 58,038 assertions, targeting linux/amd64, linux/arm64, and darwin/arm64. The upstream pin is `WebAssembly/spec` `wg-3.0` / `9d36019973201a19f9c9ebb0f10828b2fe2374aa`; WABT 1.0.41 and the reference interpreter handle text-format conversion. Historical limitations remain in the documentation. Do not mistake old failure tables for current status, or substitute aggregate counts for per-feature review. The [machine-readable baseline](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/tests/conformance/baselines/spec-v3-baseline.json) contains totals, but its `files` array is empty and each family count is zero. M0 should generate its own per-file/per-command report and reconcile totals with actual execution.

The concrete llgo portability questions concern runtime contracts, rather than Go syntax alone:

- The [standard-Go amd64 trampoline](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/src/core/runtime/trampoline_amd64.s) uses Plan 9 assembly, `NOSPLIT`, and a foreign stack. It preserves the register holding `g` and restores the ABIInternal X15 convention. Its build condition only specifies `!tinygo`; this survey found no llgo-specific path.
- The [TinyGo trampoline](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/src/core/runtime/trampoline_tinygo_amd64.go) generates machine code separately and depends on TinyGo's function-value representation and argument registers. It offers a portability approach, not an llgo implementation that can be used unchanged.
- The [architecture document](https://github.com/wago-org/wago/blob/4de27acba12926e52b815e5845e035d1cf11edd0/ARCHITECTURE.md) also describes off-heap stacks, signal guards, W^X mappings, GC root maps, and host-collector assumptions. Even if llgo can process the assembly, callbacks, GC roots, blocking, and cancellation require independent validation.

Wago is therefore a serious candidate for code reuse or porting, and a differential-testing reference. Its public evidence does not yet establish llgo compatibility, arbitrary combinations of threads and GC, or complete WIT/WASI interface coverage. Performance comparisons must pin machines, versions, configurations, and workloads; do not reuse advertised speedup factors relative to wazero as project results.

## Other Go projects

[wippyai/wasm-runtime](https://github.com/wippyai/wasm-runtime/blob/main/README.md) claims a pure-Go Component Model implementation, WIT, Canonical ABI, a P2 host, asyncify, and WAT compilation on top of wazero. It provides an existing implementation to study for component execution in Go, and illustrates separation of the component layer from the Core engine. A README claim is not proof of complete conformance, and the project cannot automatically inherit unreleased wazero GC capabilities. M0 may evaluate its component decoding, resource tables, and ABI implementation; review licenses and tests separately before importing code.

[pgavlin/warp](https://github.com/pgavlin/warp) contains Go interpreter/compiler, WAT/WAST, and wasi directories and is useful as a tooling-organization reference. It is **different from the C++ wago-org/warp project** referenced by Wago's architecture documentation. [Life](https://github.com/perlin-network/life/blob/master/README.md) offers a pure-Go interpreter and experimental AOT; its README still reports 66/72 tests. Historical test counts do not prove current Core 3, GC, or Component Model conformance. [wagon](https://github.com/go-interpreter/wagon) is also a historical reference, without a modern-feature commitment in this survey.

## Non-Go engines: references and differential testing

**Wasmtime** is the preferred reference for modern specifications and the Component Model. Its official [proposal matrix](https://docs.wasmtime.dev/stability-wasm-proposals.html) classifies GC, typed refs, and EH as Tier 1, with some Winch exceptions, and threads as Tier 2. Integration of shared memory with Store limits and pooling still has limitations. Stack switching is Tier 3 work in progress; shared-everything threads is unimplemented. Component async is enabled by default, while component threading and related features remain separately gated. These must not be combined into one blanket claim of complete multithreading.

Wasmtime's [wasi crate source](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasi/src/lib.rs) provides separate p1/p2/p3 modules and still qualifies p3 as experimental, unstable, and incomplete. The [component execution documentation](https://component-model.bytecodealliance.org/running-components/wasmtime.html) describes executing the P3 ABI. Together, these establish an executable implementation whose exact support boundary still needs version-specific verification. [wasmtime-go](https://github.com/bytecodealliance/wasmtime-go/blob/main/README.md) calls the C API through cgo; its coverage must not be assumed identical to the Rust API.

**WAMR** moved to `wasm-micro-runtime/wasm-micro-runtime`. Its [README](https://github.com/wasm-micro-runtime/wasm-micro-runtime/blob/main/README.md) lists shared memory, pthreads, wasi-threads, and a Go binding. The [build contract](https://github.com/wasm-micro-runtime/wasm-micro-runtime/blob/main/doc/build_wamr.md) narrows those claims: GC is disabled by default and is not yet fully conformant; EH is the legacy version and is limited to the classic interpreter. Use it to cross-check P1/thread-spawn integration, without treating the README feature list as complete Core 3 certification.

**WasmEdge** publishes a [proposal table](https://wasmedge.org/docs/start/wasmedge/extensions/proposals/) distinguishing interpreter support, AOT support, and default flags. GC is default from 0.16; Core threads requires a flag; Component Model support from 0.17 covers only loading and validation. It is a useful second independent reference for GC/EH, but parsing a component successfully is not the same as executing P2/P3.

**Wasmer's** [feature set](https://github.com/wasmerio/wasmer/blob/main/lib/types/src/features.rs) and [native-compiler validator](https://github.com/wasmerio/wasmer/blob/main/lib/compiler/src/compiler.rs) do not enable Wasm GC instructions. `GC_TYPES` is different from `GC`. Backends and V8 integration may differ and need separate tests. The [WASIX FAQ](https://wasix.org/docs/explanation/faqs/) describes coexistence of wasi-threads and the WASIX threading ABI. WASIX is an extension ecosystem, not a synonym for WASI P2/P3. [wasmer-go](https://github.com/wasmerio/wasmer-go/blob/master/README.md) wraps a native library through cgo.

**Browser engines** demonstrate GC ecosystem maturity, rather than WASI host support. [V8](https://v8.dev/blog/holiday-season-2023) has released GC; [Mozilla](https://bugzilla.mozilla.org/show_bug.cgi?id=2013741) records WasmGC support from Firefox 120; [WebKit Safari 18.2](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/) added GC. Threading combines Workers with SharedArrayBuffer; the [MDN shared-memory documentation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer#webassembly_shared_memory) describes the conditions for atomics and shared memory. Components and WASI in browsers generally require additional tooling and host layers. This project does not plan to embed an entire JavaScript engine in Go.

## M0: reuse decision and exit criteria

M0 is an experiment before full implementation, not a requirement to import dependencies or develop a complete VM during the research stage. Its execution order and deliverables are defined in the [development roadmap](../roadmap.md). Compare at least these paths:

| Path | Work it can reduce | Costs that need validation | Current assessment |
| --- | --- | --- | --- |
| Extend or port the wazero interpreter | Core 1/2, P1, host API, mature tests | GC type/value/validator changes; llgo compilation; internal-package boundaries; patch maintenance | Priority experiment |
| Port Wago or extract selected modules | Existing Core 3 implementation; GC/compiler/test foundations | ABI, foreign stacks, collector, signals, threading combinations, and beta API changes | Evaluate in parallel with wazero |
| Build a portable Go interpreter with selective reuse | Explicit llgo contract; GC and threading incorporated into the type model | Largest investment in decoding, validation, numeric semantics, and coverage | Retain as the design baseline; decide scope after M0 |
| Wrap Wasmtime or WAMR | Fastest access to existing capabilities; useful as an oracle | Rust/C/FFI/toolchain and binding coverage; does not meet the Go implementation goal | Testing/comparison only, not the production core |

M0 should produce a reproducible report:

1. Pin candidate commits, licenses, Go/llgo versions, and platforms. Start through public APIs with `add`, traps, host callbacks, and P1 hello world. Then run small fixtures for cyclic GC objects/forced collection, threads wait/notify, and shared memory.grow.
2. Execute the same tests under both host compilers. Distinguish build-only checks from actual execution, and record pass/fail/skip results. A successful `go build` alone is not compatibility. Go race/fuzz results do not imply equivalent llgo diagnostics.
3. Classify each failure: Go language or standard library, assembly integration, host ABI, GC roots, shared-memory behavior, or unimplemented proposal. Estimate patch scope and upstream suitability. Verify llgo memory-management behavior against the actual toolchain implementation.
4. Compare the same precompiled fixtures with Wasmtime, and validate P1 threads additionally with WAMR/Wasmer. Test GC, threads, and EH individually before combinations; independent feature support does not prove correct interaction.
5. Reuse pinned versions of official `WebAssembly/spec` / testsuite, WASI WIT, and test suites. Study Wago's WAST conversion and wazero's binary fixtures, but do not copy their pass totals, exclusion lists, or internal test results as this project's evidence. Preserve provenance, licenses, tool versions, and fixture-generation steps.
6. Produce an architecture decision record: prefer reuse if a candidate can meet Go+llgo, GC, threading, and versioned WASI goals with maintainable patches. If core ABI, GC, or ownership models require extensive rewriting, choose an independent interpreter and identify the code, tooling, and test assets retained. Both outcomes preserve `wasmvm`'s independent API and consistency contract.

License boundaries: this survey verified Apache-2.0 for wazero/Wago, MIT for Life, a BSD-3-Clause repository license marker for warp, and Apache-2.0 WITH LLVM-exception for WAMR. Reading code and studying designs has not imported implementation code. When copying any source, test, or fixture later, preserve its individual license and NOTICE requirements. A permissive engine license does not establish the license of all third-party corpus material.

## Validation not yet performed

This research stage did not build or run third-party engines, certify the candidates under llgo, rerun benchmarks or full conformance suites, or confirm that every candidate's latest release tag matches main. These experiments belong to the next implementation decision gate. The README must not describe them as capabilities already demonstrated by this project.
